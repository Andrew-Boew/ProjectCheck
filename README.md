# ProjectCheck

ProjectCheck — консольная утилита для проверки локального проекта перед публикацией. Она показывает замечания, но не изменяет проверяемые файлы.

## Требования и запуск

- Python 3.11 или новее. Сторонние Python-пакеты не нужны.
- Git нужен для учёта `.gitignore`. Без Git утилита обходит файлы напрямую.

```bash
python3 projectcheck.py /путь/к/проекту
python3 projectcheck.py /путь/к/проекту --format json
python3 projectcheck.py /путь/к/проекту --fail-on-findings
python3 projectcheck.py /путь/к/проекту --fail-on-security
python3 projectcheck.py /путь/к/проекту --staged
```

## Проверка перед коммитом

Для самого ProjectCheck после клонирования включите hook из репозитория:

```bash
git config core.hooksPath .githooks
```

GitHub Actions запускает тесты и строгую проверку ProjectCheck на каждый push и pull request. Для проверки другого репозитория установите в нём локальный hook:

```bash
python3 projectcheck.py /путь/к/проекту --install-hook
```

При `git commit` hook запускает ProjectCheck с `--staged --fail-on-security`. Коммит останавливается при `SENSITIVE`, `HARDCODED_SECRET`, `PRIVATE_KEY_BLOCK` или `SCAN_ERROR`. Остальные замечания показываются, но не блокируют коммит. После исправления файлов запустите `git add` ещё раз. Для строгой проверки всех замечаний используйте `--fail-on-findings` вручную. Hook в `.githooks` хранится в репозитории, но Git использует его только после настройки `core.hooksPath` в каждом клоне. Установка через `--install-hook` создаёт локальный hook в выбранном репозитории. Повторная установка обновляет hook, созданный предыдущей версией ProjectCheck; чужой `pre-commit` остаётся без изменений. Локальный hook сохраняет абсолютный путь к этому экземпляру `projectcheck.py`; после переноса ProjectCheck установите его заново.

Если переданная папка является корнем Git-репозитория, проверяются отслеживаемые и новые неигнорируемые файлы. Файл, уже добавленный в Git, проверяется даже при наличии правила для него в `.gitignore`. Содержимое читается с диска. Если подготовленная к коммиту версия файла отличается от версии на диске, выводится `SCAN_ERROR`: содержимое коммита в этом случае не проверено. `--staged` проверяет содержимое обычных файлов непосредственно из Git index, включая подготовленные удаления и изменения; для него требуется корень Git-репозитория. Новые файлы попадут в этот режим после `git add`. Для обычной папки выполняется прямой обход. Каталоги `.git`, `.venv`, `venv`, `node_modules`, `__pycache__` и символические ссылки пропускаются.

## Проверки

| Код | Что проверяется |
| --- | --- |
| `README` | Наличие `README.md`, `README.rst` или `README.txt` в корне |
| `GITIGNORE` | Наличие `.gitignore` в корне |
| `TESTS` | Наличие Python-файла `test_*.py` или `*_test.py` |
| `SENSITIVE` | Имена `.env`, `.env.*`, `id_rsa`, `id_ed25519`, `id_ecdsa`, `id_dsa` и расширения `.key`, `.p12`, `.pfx` |
| `HARDCODED_SECRET` | Непустые строковые значения секретных полей в Python, JSON, TOML и YAML-конфигурациях, а также заполненные секретные переменные в `.env` |
| `PRIVATE_KEY_BLOCK` | Заголовок PEM/OpenSSH-блока приватного ключа внутри файла |
| `TEMP` | Расширения `.tmp`, `.bak`, `.swp`, `.swo`, имена с `~` на конце и `.DS_Store` |
| `LARGE` | Файлы больше заданного порога, по умолчанию 10 МиБ |
| `LICENSE` | Наличие файла лицензии в корне |
| `CI` | Наличие конфигурации GitHub Actions, GitLab CI, CircleCI, Travis CI, Azure Pipelines или Jenkins |
| `DEPENDENCY_LOCK` | Наличие lock-файла рядом с корневым `package.json` |
| `UNPINNED_DEPENDENCY` | Зависимость без точной версии в `requirements.txt` или `requirements-dev.txt` |
| `SCAN_ERROR` | Ошибка чтения, получения размера файла или расхождение подготовленной и рабочей версии |

Для `.env.example`, `.env.sample` и `.env.template` предупреждение `SENSITIVE` не создаётся, и их содержимое не проверяется на заполненные переменные. Проверка `HARDCODED_SECRET` разбирает `settings.py`, `config.py`, `settings.json`, `config.json`, `appsettings.json`, `settings.toml`, `config.toml`, `pyproject.toml`, проверяемые `.env`-файлы, YAML-файлы с именами `settings`, `config`, `application`, `compose`, `docker-compose` или `values` и расширением `.yml`/`.yaml`, а также конфигурации CI. Значение секрета в отчёт не выводится. Пустые значения и ссылки вида `${VAR}` или `${{ secrets.VAR }}`, а также присваивание через `os.getenv()` в Python не считаются захардкоженным значением. Для JSON/TOML номер строки пока не определяется. YAML проверяется по простым строковым шаблонам, без полного разбора синтаксиса; возможны пропуски и ложные срабатывания. `PRIVATE_KEY_BLOCK` просматривает первые 2 МиБ каждого файла, включая шаблоны. Проверка `TESTS` пока распознаёт только Python-тесты. Правила зависимостей покрывают корневой npm lock-файл и обычные записи в двух файлах requirements; они не проверяют уязвимости пакетов или наличие опубликованных версий. Правило `CI` проверяет наличие конфигурации, но не выполняет pipeline.

## Настройки

В корне проверяемого проекта можно создать `.projectcheck.toml`:

```toml
max_size_mib = 20
exclude = ["generated/", "*.bak"]
```

`max_size_mib` — положительное целое число. `exclude` — список путей и шаблонов относительно корня проекта. Запись `generated/` исключает папку целиком, `*.bak` — подходящие файлы.

Параметры можно задать и при запуске:

```bash
python3 projectcheck.py . --max-size-mib 5 --exclude 'generated/' --exclude '*.bak'
```

Порог из командной строки заменяет значение из TOML. Исключения из командной строки добавляются к исключениям из TOML.

## Отчёт и код завершения

Текстовый отчёт выводится по умолчанию. `--format json` выводит объект с полями `project`, `count` и `findings`. Каждое замечание содержит `code`, `message`, `path`, `line` и `confidence`. Для проверок проекта в целом `path` и `line` равны `null`. Уверенность (`high`, `medium`, `low`) показывает надёжность срабатывания правила, а не важность проблемы. Строка отображается и в текстовом отчёте как `путь:номер`.

| Код завершения | Значение |
| --- | --- |
| `0` | Проверка завершилась; замечания допускаются без строгого режима или вне правил безопасности в `--fail-on-security` |
| `1` | Есть замечания с `--fail-on-findings` либо находки безопасности с `--fail-on-security` |
| `2` | Ошибка аргументов, конфигурации или неполная проверка (`SCAN_ERROR`) |
